# Quickstart: Arabic Fuzzy Product Search

These are validation steps for the implementer or reviewer. Per `AGENTS.md`, AI agents must not run the commands in this repository.

## Prerequisites

- Local database is available with the project environment configured.
- The feature migration has been created and applied by the developer.
- Prisma Client has been regenerated by the developer after schema changes.
- Non-production seed data includes Arabic spelling variants such as `آيه`, `ايه`, and `اية` for the same tenant.

## Manual Commands For The User To Run

Run these only after implementation:

```bash
cd backend
pnpm prisma:migrate:dev
pnpm prisma:generate
pnpm test:e2e
pnpm lint:ci
```

If unit test scripts are added for backend specs, run those before e2e tests and share the output.

## Validation Scenario 1: Arabic Variants Match

1. Seed one tenant with products named `آيه`, `ايه`, and `اية`.
2. Search that tenant's products with `search=آيه`.
3. Search the same tenant with `search=ايه`.
4. Search the same tenant with `search=اية`.

Expected result: each query returns all intended variant products within the first 5 results.

## Validation Scenario 2: Tenant Isolation

1. Seed tenant A and tenant B with similar Arabic product names.
2. Search tenant A through authenticated merchant search.
3. Search tenant A through the public storefront slug.

Expected result: tenant B products never appear in tenant A search responses.

## Validation Scenario 3: Empty Query Rejection

1. Request product search with `search=` or whitespace-only text.

Expected result: validation rejects the request and no product list is returned.

## Validation Scenario 4: Pagination Stability

1. Seed more matching products than the page limit.
2. Request page 1 and page 2 for the same search term and limit.

Expected result: page metadata is correct, page 2 does not duplicate page 1 results, and ordering remains stable.

## Validation Scenario 5: Ranking

1. Seed exact, near-exact, contains, and weak Arabic matches for a term.
2. Search with the exact or near-exact term.

Expected result: exact and near-exact normalized matches rank above weaker matches in representative cases.

## Validation Scenario 6: Query Plan

Ask the database to explain the implemented product search query against a few thousand product rows.

Expected result: the plan uses the normalized product-name trigram index where selective enough and does not rely on a broad sequential scan for normal tenant-scoped searches.

Example SQL shape to adapt with real tenant/search values:

```sql
EXPLAIN ANALYZE
SELECT product.*,
  word_similarity(product.name_normalized, arabic_normalize('ايه')) AS word_sim,
  similarity(product.name_normalized, arabic_normalize('ايه')) AS name_similarity
FROM products product
INNER JOIN tenants tenant ON product.tenant_id = tenant.id
WHERE tenant.slug = '<tenant-slug>'
  AND product.status = 'active'
  AND product.deleted_at IS NULL
  AND (
    product.name_normalized LIKE 'ايه%'
    OR product.name_normalized LIKE '%ايه%'
    OR (
      similarity(product.name_normalized, arabic_normalize('ايه')) >= 0.32
      AND word_similarity(product.name_normalized, arabic_normalize('ايه')) >= 0.58
    )
  )
ORDER BY word_sim DESC, name_similarity DESC, product.created_at DESC, product.id DESC
LIMIT 20 OFFSET 0;
```

## Validation Scenario 7: Latency

1. Seed a merchant catalog with a few thousand products.
2. Run the public and authenticated search flows for 10 representative Arabic queries.
3. Capture the first-page request duration for each query from the client or server logs.

Expected result: first-page search responses complete in under 1 second under normal local or staging conditions.

## Notes

- Do not change catalog source visibility rules while validating product search.
- If search quality or volume later outgrows PostgreSQL trigram ranking, a dedicated search engine is the natural next step behind the same product-search contract.
